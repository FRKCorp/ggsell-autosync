## 2. Архитектура FazerCards (источник товара) — уже понятна полностью

Один HTTP-префикс `/api/v2`, `X-API-Key`. Отдельные лимиты по категориям запросов (см. код клиента). Идемпотентность на всех create-заказ эндпоинтах через `Idempotency-Key`. Основные группы: `/topups`, `/giftcards`, `/gamekeys`, `/steam-gifts`, `/steam-topup`, `/manual-services`, плюс `/orders` для поллинга статуса.

## 3. Архитектура GGSell — то, что выяснили сегодня

### 3.1. Нужны ОБЕ версии API одновременно, не одна

| | V1 | V2 |
|---|---|---|
| Auth | логин+пароль → токен (`POST /api_sellers/api/apilogin`) | статичный API-ключ в `Authorization` (из личного кабинета) |
| Что есть | Account, Categories, **Chats**, Products (bulk price), **Orders** (`return-last-sales`, `get-order-info`, `check-unique-code`), Reviews | Category, **Options**, Products, **Offers** (list/create/get/patch/batch-activate/pause/delete) |
| Роль в проекте | обработка заказов, выдача товара через чат | автозалив каталога, обновление цен |

**Вывод:** обработка заказов идёт через V1, синхронизация каталога и цен — через V2. Два разных механизма авторизации в одном клиенте (или два отдельных клиента — `ggsell_v1.py` / `ggsell_v2.py`, решим при реализации).

### 3.2. Модель каталога V2: Offer → Option → Variant

- **Offer** — сам лот. Обязательные поля при создании: `title_ru/en`, `description_ru/en`, `instructions_ru/en`, `cover_image_ru` (base64!), `price`, `category_id` (совместим с V1-категориями), `delivery` (`auto`/`manual`). `currency` всегда `RUB`.
- **Option** — поле, которое видит/заполняет покупатель при оформлении заказа. Типы: `text`, `multiline_text`, `check_box`, `radio_button`. Прикрепляется **отдельным вызовом после создания оффера**: `POST /api_sellers/v2/offers/:offer_id/options`.
- **Variant** — модификатор цены внутри опции (не отдельный SKU!). `discount_type: fixed|percent`, `impact_type: increase|decrease`. То есть один оффер с одной опцией-`radio_button` и вариантами внутри — это способ сделать "один лот, несколько номиналов с разной ценой" (актуально для топапов типа PUBG UC/Robux).

**Архитектурное решение по мапингу FazerCards → GGSell (предварительное, обсудить с клиентом):**
- **Топапы/подарочные карты одной игры/сервиса** → один Offer + одна опция `radio_button` с вариантами на каждый номинал. Ближе к тому, как выглядят лоты у нормальных продавцов, но добавляет слой синхронизации variants.
- **Steam-гифты** → один Offer на игру (номиналы не нужны), с обязательной `text`-опцией под `invite_url` (получаем значение через `options[].user_data` в заказе).
- Для MVP можно начать с более простой модели (один Offer = один SKU FazerCards, без вариантов) и вынести группировку через variants на вторую итерацию — это дешевле по времени, но даст 2000+ почти одинаковых лотов на витрине. Нужно решить с клиентом.

### 3.3. Поток заказа

1. Покупатель оформляет заказ на Offer, заполняет Option (вводит `invite_url`/Player ID и т.п.) → это попадает в `options[].user_data` заказа.
2. Мы узнаём о заказе (см. 3.4 — вебхук вместо поллинга).
3. Достаём данные заказа: `GET /api_sellers/api/purchase/info/:invoice_id` (V1) → структура `info_order`, включая `options[].user_data`, `buyer_info`, `unique_code_state`.
4. Заказываем у FazerCards (используя данные из `user_data`), ждём выполнения.
5. Отправляем код/инструкцию покупателю **через чат заказа** (V1, `Chats`/`create-message-without-file`) — это и есть механизм выдачи (`id_i` = `invoice_id`, см. 6.4). Офферы при этом с `delivery: auto` (см. 3.8).
6. ~~Формально закрываем заказ на стороне GGSell~~ — такого эндпоинта нет, шаг не нужен (см. 3.6).

`unique_code_state.state` (числовой код) — состояние подтверждения покупателем факта получения (`date_check/date_delivery/date_confirmed/date_refuted`). Есть `day_lock`/`lock_state` в заказе — похоже на заморозку выплаты продавцу на N дней, механику пока не разбирали детально, не блокер.

### 3.4. Вебхук вместо поллинга — важная находка

При создании/патче Offer можно задать `notification_settings: {type: "url", url, http_method: GET|POST, is_disabled, is_default}` — GGSell сам уведомляет наш сервер о новой продаже **на каждый оффер** (не глобальная настройка). Это заменяет постоянный поллинг `return-last-sales` из V1 на реалтайм-приём. При автозаливе черновиков сразу проставляем этот вебхук всем офферам.

## 3.5. Дополнительно найдено при повторном обходе навигации

- **V1 bulk price update**: `POST /api_sellers/api/product/edit/prices` — "updates prices of products and variants in bulk". Кандидат на замену поштучных V2 `PATCH /offers/:id` при синхронизации 2000 позиций — сравнить оба подхода по количеству запросов/лимитам, когда будет готов клиент.
- **V2 Products** полностью: List/Create/Archive products + List/Create/Archive splitted products (`/api_sellers/v2/offers/:offer_id/products`) — это преднагруженный сток для `is_autoselling` (не наш случай — товар у нас не преднагружен, покупаем у FZ в момент заказа — но держим в голове).
- **Полностью прошли по всем разделам V1 и V2** — отдельного эндпоинта "подтвердить/закрыть доставку" нигде нет. Либо это неявный флаг внутри `create-message-without-file` (нужно посмотреть развёрнутое тело запроса), либо доступно только из веб-интерфейса без API — уточняем это следующим шагом.

## 3.6. create-message-without-file — схема выдачи окончательно ясна

`POST /api_sellers/api/debates/v2`, query: `token` (V1-токен), `id_i` (~~id чата из `list-of-chats`~~ — **исправлено 27 сентября: это номер заказа `invoice_id`**, см. 6.4), тело: `{"message": "string"}`. Флага "пометить как доставлено" в теле НЕТ.

**Решение (не временный пробел, а факт):** отдельного API-вызова для закрытия/подтверждения доставки у GGSell нет вообще (проверено по всем разделам V1/V2). Наш `orders/`-модуль просто отправляет сообщение с кодом в чат через `create-message` и считает это финалом happy path — без отдельного шага «закрыть заказ». Статус доставки, видимо, управляется только через `unique_code_state` самим покупателем (подтверждает/оспаривает), без участия продавца через API.

## 3.7. V1 auth — схема подписи ясна

`POST /api_sellers/api/apilogin`: `{seller_id, timestamp (unix), sign}`, где `sign = SHA256(api_key + timestamp)`. Ответ: `{retval, desc, token, seller_id, valid_thru}` — токен имеет срок жизни (`valid_thru`), клиент должен сам обновлять перед истечением.

**Важно:** `api_key` в формуле подписи — это отдельный V1-ключ (не тот же статичный ключ, что используется в `Authorization` для V2), и нужен ещё `seller_id`. Найти их надо в личном кабинете GGSell (раздел с API/профилем продавца) — отдельно от V2-ключа.

## 3.8. `delivery: auto` — подтверждено поддержкой GGSell, вопрос закрыт окончательно

Поддержка GGSell прямо подтвердила: метода изменить чекбокс «Сразу помечать как доставленный» через API не существует вообще (ответ техподдержки: «на текущий момент у нас нет метода, позволяющего изменить данную настройку»). Вопрос закрыт, не требует дальнейшего ресёрча. Работаем по схеме: `delivery: auto` на всех офферах, выдача через чат (`create_message`), риск при молчании FZ — принят.

## 3.10. Steam и Telegram — отдельные эндпоинты FazerCards, не часть /topups

На верхнем уровне доков FazerCards есть отдельные группы «Steam» и «Telegram», не пересекающиеся с `/topups` — поэтому их не было в списке из 306 категорий topup.

- **`/steam-topup`** (Steam — RUB/KZT/UAH из списка клиента): НЕ каталог с фиксированными офферами — прямое пополнение на произвольную сумму: `GET /steam-topup/rates` (курсы USD→RUB/UAH/KZT), `POST /steam-topup/check-login` (проверка логина), `POST /steam-topup/order` с `{steamLogin, currency, amount}`. Не укладывается в модель `Position` (там всё исходит из фиксированной цены за конкретный SKU) — нужен отдельный механизм, ближе к прайсеру (лот на GGSell с произвольной суммой/калькулятором, а не фиксированный SKU).
- **`/telegram`**: `GET/POST /telegram/premium(/buy)` — 3 фиксированных плана (3/6/12 месяцев, цена в USD) — это укладывается в `Position` как обычные 3 позиции. `GET/POST /telegram/stars(/buy)` — цена за 1 звезду (`price_per_star`), покупатель указывает количество — тоже динамическая цена, не фиксированный SKU.

В `fazercards.py` эти эндпоинты ещё не реализованы — добавить, когда дойдём до этих позиций по факту.

## 3.12. Деплой на VPS (22 сентября)

Проект развёрнут на реальном сервере: домен `frkcorp.online` (reg.ru, A-запись на IP VPS), Docker Compose с сервисами `db` (Postgres, порт закрыт на `127.0.0.1`, не наружу), `app` (FastAPI, вебхуки), `scheduler` (`app.sync.main`), `caddy` (реверс-прокси с авто-HTTPS через Let's Encrypt). Обе миграции Alembic применены на серверной БД. `/health` отвечает `{"ok": true}` по HTTPS — вся цепочка домен → Caddy → приложение работает.

`docker-compose.yml` больше не хранит креды хардкодом — читает из `.env` (`POSTGRES_USER/PASSWORD/DB`), которого нет в репозитории. На сервере `.env` отличается от локального: `DATABASE_URL` использует хост `db` (не `localhost`), `GGSELL_WEBHOOK_URL` указывает на реальный домен.

## 3.13. Первый живой вебхук — формат подтверждён, chat_id всё ещё не решён

Подтверждено на реальной покупке тестового оффера:

- **Вебхук — POST с JSON-телом**, НЕ query-параметры (описание в личном кабинете вводит в заблуждение). Реальные поля отличаются от описанных: `{"id_i": ..., "id_d": ..., "amount": "1.0", "currency": "RUB", "email": ..., "date": ..., "ip": ..., "SHA256": ..., "is_my_product": true}` — не `curr`/`sha256`/`isMyProduct`, как в описании UI.
- **`id_i` = `invoice_id`** — подтверждено: совпадает с номером заказа, видимым покупателю, и с `content_id` из ответа `get_order_info`.
- **`id_d` = `item_id` = `Listing.ggsell_offer_id`** — подтверждено: совпадает с `item_id` из `get_order_info` для того же заказа. Открытый вопрос №[item_id соответствие] закрыт.
- `get_order_info` целиком отработал корректно на реальном заказе — структура ответа соответствует ранее задокументированной схеме `info_order`.

**НЕ решено — `chat_id` для `create_message`** (история поиска; **решено 27 сентября, см. 6.4** — `id_i` это `invoice_id`, всё ниже неактуально):
- Задокументированный `GET /api_sellers/api/debates/v2/chats` (путь подтверждён по Swagger, не выдумка) возвращает записи с ВСЕМИ полями `null` (кроме даты последнего сообщения) — не даёт рабочий `id_i` чата. Похоже на тот же паттерн, что и с `delivery`: задокументированный метод не функционирует по факту.
- Через DevTools найден реальный работающий путь — но это **другой, внутренний бэкенд** `seller.ggsel.com/api/v1/conversations` с `conversation_id` (например, `32317397`), авторизация `Bearer`-JWT из **настоящей браузерной сессии** залогиненного пользователя. Это НЕ статичный API-ключ и не наша V1-подпись — токен привязан к сессии реального логина, будет истекать, и использовать его для неконтролируемого сервера — плохая идея (хрупко, не для этого предназначено, может сломаться без предупреждения).
- Найдена связка `order_id ↔ conversation_id ↔ offer.id` в ответе внутреннего эндпоинта (`GET .../conversations` или `.../messages` — оба присутствуют в объекте сообщения), но это не помогает, раз сам эндпоинт требует браузерную сессию.
- **Отправлен вопрос в поддержку GGSell** (по аналогии с вопросом про `delivery`): как через официальный API получить `id_i` чата по номеру заказа, раз `list-of-chats` возвращает пустые записи. Ждём ответа.
- Пока ждём — `orders/order_processor.py` реализует всё до этого шага (webhook → `get_order_info` → маппинг на `Listing` → заказ у FazerCards), последний шаг (отправка сообщения в чат) остаётся TODO с понятной точкой вставки в коде.
