## 2. Архитектура FazerCards (источник товара) — уже понятна полностью

Один HTTP-префикс `/api/v2`, `X-API-Key`. Отдельные лимиты по категориям запросов (см. код клиента). Идемпотентность на всех create-заказ эндпоинтах через `Idempotency-Key`. Основные группы: `/topups`, `/giftcards`, `/gamekeys`, `/steam-gifts`, `/steam-topup`, `/manual-services`, плюс `/orders` для поллинга статуса.

## 3. Архитектура GGSell — то, что выяснили сегодня

### 3.1. Нужны ОБЕ версии API одновременно, не одна

| | V1 | V2 |
|---|---|---|
| Auth | логин+пароль → токен (`POST /api_sellers/api/apilogin`) | статичный API-ключ в `Authorization` (из личного кабинета) |
| Что есть | Account, Categories, **Chats**, Products (bulk price), **Orders** (`return-last-sales`, `get-order-info`, `check-unique-code`), Reviews | Category, **Options**, Products, **Offers** (list/create/get/patch/batch-activate/pause/delete) |
| Роль в проекте | обработка заказов, выдача товара через чат | автозалив каталога, обновление цен |

**Вывод:** обработка заказов идёт через V1, синхронизация каталога и цен — через V2. Два разных механизма авторизации в одном клиенте (или два отдельных клиента — `ggsell_v1.py` / `ggsell_v2.py`, решим при реализации).

### 3.2. Модель каталога V2: Offer → Option → Variant

- **Offer** — сам лот. Обязательные поля при создании: `title_ru/en`, `description_ru/en`, `instructions_ru/en`, `cover_image_ru` (base64!), `price`, `category_id` (совместим с V1-категориями), `delivery` (`auto`/`manual`). `currency` всегда `RUB`.
- **Option** — поле, которое видит/заполняет покупатель при оформлении заказа. Типы: `text`, `multiline_text`, `check_box`, `radio_button`. Прикрепляется **отдельным вызовом после создания оффера**: `POST /api_sellers/v2/offers/:offer_id/options`.
- **Variant** — модификатор цены внутри опции (не отдельный SKU!). `discount_type: fixed|percent`, `impact_type: increase|decrease`. То есть один оффер с одной опцией-`radio_button` и вариантами внутри — это способ сделать "один лот, несколько номиналов с разной ценой" (актуально для топапов типа PUBG UC/Robux).

**Архитектурное решение по мапингу FazerCards → GGSell (предварительное, обсудить с клиентом):**
- **Топапы/подарочные карты одной игры/сервиса** → один Offer + одна опция `radio_button` с вариантами на каждый номинал. Ближе к тому, как выглядят лоты у нормальных продавцов, но добавляет слой синхронизации variants.
- **Steam-гифты** → один Offer на игру (номиналы не нужны), с обязательной `text`-опцией под `invite_url` (получаем значение через `options[].user_data` в заказе).
- Для MVP можно начать с более простой модели (один Offer = один SKU FazerCards, без вариантов) и вынести группировку через variants на вторую итерацию — это дешевле по времени, но даст 2000+ почти одинаковых лотов на витрине. Нужно решить с клиентом.

### 3.3. Поток заказа

1. Покупатель оформляет заказ на Offer, заполняет Option (вводит `invite_url`/Player ID и т.п.) → это попадает в `options[].user_data` заказа.
2. Мы узнаём о заказе (см. 3.4 — вебхук вместо поллинга).
3. Достаём данные заказа: `GET /api_sellers/api/purchase/info/:invoice_id` (V1) → структура `info_order`, включая `options[].user_data`, `buyer_info`, `unique_code_state`.
4. Заказываем у FazerCards (используя данные из `user_data`), ждём выполнения.
5. Отправляем код/инструкцию покупателю **через чат заказа** (V1, `Chats`/`create-message-without-file`) — это и есть механизм выдачи (`id_i` = `invoice_id`, см. 6.4). Офферы при этом с `delivery: auto` (см. 3.8).
6. ~~Формально закрываем заказ на стороне GGSell~~ — такого эндпоинта нет, шаг не нужен (см. 3.6).

`unique_code_state.state` (числовой код) — состояние подтверждения покупателем факта получения (`date_check/date_delivery/date_confirmed/date_refuted`). Есть `day_lock`/`lock_state` в заказе — похоже на заморозку выплаты продавцу на N дней, механику пока не разбирали детально, не блокер.

### 3.4. Вебхук вместо поллинга — важная находка

При создании/патче Offer можно задать `notification_settings: {type: "url", url, http_method: GET|POST, is_disabled, is_default}` — GGSell сам уведомляет наш сервер о новой продаже **на каждый оффер** (не глобальная настройка). Это заменяет постоянный поллинг `return-last-sales` из V1 на реалтайм-приём. При автозаливе черновиков сразу проставляем этот вебхук всем офферам.

## 3.5. Дополнительно найдено при повторном обходе навигации

- **V1 bulk price update**: `POST /api_sellers/api/product/edit/prices` — "updates prices of products and variants in bulk". Кандидат на замену поштучных V2 `PATCH /offers/:id` при синхронизации 2000 позиций — сравнить оба подхода по количеству запросов/лимитам, когда будет готов клиент.
- **V2 Products** полностью: List/Create/Archive products + List/Create/Archive splitted products (`/api_sellers/v2/offers/:offer_id/products`) — это преднагруженный сток для `is_autoselling` (не наш случай — товар у нас не преднагружен, покупаем у FZ в момент заказа — но держим в голове).
- **Полностью прошли по всем разделам V1 и V2** — отдельного эндпоинта "подтвердить/закрыть доставку" нигде нет. Либо это неявный флаг внутри `create-message-without-file` (нужно посмотреть развёрнутое тело запроса), либо доступно только из веб-интерфейса без API — уточняем это следующим шагом.

## 3.6. create-message-without-file — схема выдачи окончательно ясна

`POST /api_sellers/api/debates/v2`, query: `token` (V1-токен), `id_i` (~~id чата из `list-of-chats`~~ — **исправлено 27 сентября: это номер заказа `invoice_id`**, см. 6.4), тело: `{"message": "string"}`. Флага "пометить как доставлено" в теле НЕТ.

**Решение (не временный пробел, а факт):** отдельного API-вызова для закрытия/подтверждения доставки у GGSell нет вообще (проверено по всем разделам V1/V2). Наш `orders/`-модуль просто отправляет сообщение с кодом в чат через `create-message` и считает это финалом happy path — без отдельного шага «закрыть заказ». Статус доставки, видимо, управляется только через `unique_code_state` самим покупателем (подтверждает/оспаривает), без участия продавца через API.

## 3.7. V1 auth — схема подписи ясна

`POST /api_sellers/api/apilogin`: `{seller_id, timestamp (unix), sign}`, где `sign = SHA256(api_key + timestamp)`. Ответ: `{retval, desc, token, seller_id, valid_thru}` — токен имеет срок жизни (`valid_thru`), клиент должен сам обновлять перед истечением.

**Важно:** `api_key` в формуле подписи — это отдельный V1-ключ (не тот же статичный ключ, что используется в `Authorization` для V2), и нужен ещё `seller_id`. Найти их надо в личном кабинете GGSell (раздел с API/профилем продавца) — отдельно от V2-ключа.

## 3.8. `delivery: auto` — подтверждено поддержкой GGSell, вопрос закрыт окончательно

Поддержка GGSell прямо подтвердила: метода изменить чекбокс «Сразу помечать как доставленный» через API не существует вообще (ответ техподдержки: «на текущий момент у нас нет метода, позволяющего изменить данную настройку»). Вопрос закрыт, не требует дальнейшего ресёрча. Работаем по схеме: `delivery: auto` на всех офферах, выдача через чат (`create_message`), риск при молчании FZ — принят.

## 3.10. Steam и Telegram — отдельные эндпоинты FazerCards, не часть /topups

На верхнем уровне доков FazerCards есть отдельные группы «Steam» и «Telegram», не пересекающиеся с `/topups` — поэтому их не было в списке из 306 категорий topup.

- **`/steam-topup`** (Steam — RUB/KZT/UAH из списка клиента): НЕ каталог с фиксированными офферами — прямое пополнение на произвольную сумму: `GET /steam-topup/rates` (курсы USD→RUB/UAH/KZT), `POST /steam-topup/check-login` (проверка логина), `POST /steam-topup/order` с `{steamLogin, currency, amount}`. Не укладывается в модель `Position` (там всё исходит из фиксированной цены за конкретный SKU) — нужен отдельный механизм, ближе к прайсеру (лот на GGSell с произвольной суммой/калькулятором, а не фиксированный SKU).
- **`/telegram`**: `GET/POST /telegram/premium(/buy)` — 3 фиксированных плана (3/6/12 месяцев, цена в USD) — это укладывается в `Position` как обычные 3 позиции. `GET/POST /telegram/stars(/buy)` — цена за 1 звезду (`price_per_star`), покупатель указывает количество — тоже динамическая цена, не фиксированный SKU.

В `fazercards.py` эти эндпоинты ещё не реализованы — добавить, когда дойдём до этих позиций по факту.

## 3.12. Деплой на VPS (22 сентября)

Проект развёрнут на реальном сервере: домен `frkcorp.online` (reg.ru, A-запись на IP VPS), Docker Compose с сервисами `db` (Postgres, порт закрыт на `127.0.0.1`, не наружу), `app` (FastAPI, вебхуки), `scheduler` (`app.sync.main`), `caddy` (реверс-прокси с авто-HTTPS через Let's Encrypt). Обе миграции Alembic применены на серверной БД. `/health` отвечает `{"ok": true}` по HTTPS — вся цепочка домен → Caddy → приложение работает.

`docker-compose.yml` больше не хранит креды хардкодом — читает из `.env` (`POSTGRES_USER/PASSWORD/DB`), которого нет в репозитории. На сервере `.env` отличается от локального: `DATABASE_URL` использует хост `db` (не `localhost`), `GGSELL_WEBHOOK_URL` указывает на реальный домен.

## 3.13. Первый живой вебхук — формат подтверждён, chat_id всё ещё не решён

Подтверждено на реальной покупке тестового оффера:

- **Вебхук — POST с JSON-телом**, НЕ query-параметры (описание в личном кабинете вводит в заблуждение). Реальные поля отличаются от описанных: `{"id_i": ..., "id_d": ..., "amount": "1.0", "currency": "RUB", "email": ..., "date": ..., "ip": ..., "SHA256": ..., "is_my_product": true}` — не `curr`/`sha256`/`isMyProduct`, как в описании UI.
- **`id_i` = `invoice_id`** — подтверждено: совпадает с номером заказа, видимым покупателю, и с `content_id` из ответа `get_order_info`.
- **`id_d` = `item_id` = `Listing.ggsell_offer_id`** — подтверждено: совпадает с `item_id` из `get_order_info` для того же заказа. Открытый вопрос №[item_id соответствие] закрыт.
- `get_order_info` целиком отработал корректно на реальном заказе — структура ответа соответствует ранее задокументированной схеме `info_order`.

**НЕ решено — `chat_id` для `create_message`** (история поиска; **решено 27 сентября, см. 6.4** — `id_i` это `invoice_id`, всё ниже неактуально):
- Задокументированный `GET /api_sellers/api/debates/v2/chats` (путь подтверждён по Swagger, не выдумка) возвращает записи с ВСЕМИ полями `null` (кроме даты последнего сообщения) — не даёт рабочий `id_i` чата. Похоже на тот же паттерн, что и с `delivery`: задокументированный метод не функционирует по факту.
- Через DevTools найден реальный работающий путь — но это **другой, внутренний бэкенд** `seller.ggsel.com/api/v1/conversations` с `conversation_id` (например, `32317397`), авторизация `Bearer`-JWT из **настоящей браузерной сессии** залогиненного пользователя. Это НЕ статичный API-ключ и не наша V1-подпись — токен привязан к сессии реального логина, будет истекать, и использовать его для неконтролируемого сервера — плохая идея (хрупко, не для этого предназначено, может сломаться без предупреждения).
- Найдена связка `order_id ↔ conversation_id ↔ offer.id` в ответе внутреннего эндпоинта (`GET .../conversations` или `.../messages` — оба присутствуют в объекте сообщения), но это не помогает, раз сам эндпоинт требует браузерную сессию.
- **Отправлен вопрос в поддержку GGSell** (по аналогии с вопросом про `delivery`): как через официальный API получить `id_i` чата по номеру заказа, раз `list-of-chats` возвращает пустые записи. Ждём ответа.
- Пока ждём — `orders/order_processor.py` реализует всё до этого шага (webhook → `get_order_info` → маппинг на `Listing` → заказ у FazerCards), последний шаг (отправка сообщения в чат) остаётся TODO с понятной точкой вставки в коде.

### 6.9. Опции покупателя на GGSell — проверено на живом API (30 сентября)

**Документация GGSell** — `https://seller.ggsel.com/docs` (Docusaurus). Боковое меню подгружается скриптом, полный список страниц эндпоинтов удобно доставать из бандла `assets/js/main.*.js` (строки `"/docs/v2/..."`). Схемы — `/docs/v2/schemas/<name>`.

Реализация — `app/offers/options.py` (`build_topup_options`, `attach_topup_options`, `map_buyer_data_to_fz_fields`), проверка — `scripts/test_attach_options.py` на тестовом оффере (создан, опции повешены, удалён).

- **Опции и варианты создаются раздельно.** `POST /api_sellers/v2/offers/:offer_id/options` с `{"options": [...]}` — поля `variants` в этом запросе нет (раньше в докстринге клиента было ошибочно «варианты внутри опции»). Варианты — `POST /offers/:offer_id/options/:option_id/variants` с `{"variants": [...]}`. Список — `GET /offers/:offer_id/options` отдаёт **массив** опций с вложенными `variants`.

Решение: по умолчанию — заглушка «— выберите сервер —»; реальный сервер по умолчанию ставить нельзя (невнимательный покупатель получит пополнение на аккаунт с тем же ID на другом сервере). Если заглушка осталась выбранной — заказ уходит в ручной разбор.
- **Сбой между опциями и вариантами реален** (так и случилось на первом прогоне: опции создались, варианты упали с 422). Поэтому `attach_topup_options` повторяемая: существующие опции (по `title_ru`) не создаёт заново, варианты досоздаёт только там, где их нет. Проверено на живом оффере: повторный запуск не плодит дубли.
- **Пути batch-методов — через подчёркивание:** `/offers/batch_activate`, `/offers/batch_pause`, `/offers/batch_delete`. Дефисный вариант (был в клиенте) → 404 — активация лотов и пауза из бота не работали бы. Не больше **100 id** за вызов.

**Обратный перевод при заказе** (`order_processor`): данные покупателя приходят как `{название опции: значение}`; для топапа они переводятся в `{key FZ: value FZ}` по `fields` из того же ответа `get_topup_offers`, что и перепроверка цены (без лишнего запроса). ### 6.13. Курс и наценка (1 октября, roadmap 3.4, 3.4b)

- **У GGSell нет своего курса.** В документации V1/V2 нет эндпоинта курсов. Цены в других валютах есть в V1 `GET /api_sellers/api/products/:id/data` → `product.prices.default` (`RUB`, `USD`, `EUR`) — по ним видно, как GGSell пересчитывает: черновик за 100 000 ₽ → 1196.76 $ и 1053.95 €, то есть 83.5589 ₽/$ и 94.8812 ₽/€ при ЦБ на 01.10 — 83.5588 и 94.8810. **GGSell пересчитывает ровно по ЦБ.** Значит, «курс GGSell» из пожелания клиента = ЦБ, и работаем по его запасному варианту: **ЦБ + 5%**.
- Нюанс метода: V1 product info не видит **черновики** (404 «Не найдено» даже через 90 с после создания) — отдаёт данные только для опубликованных/архивных офферов. Для зонда курса это и не понадобилось.
- **Источники ЦБ:** `https://www.cbr.ru/scripts/XML_daily.asp` (XML, windows-1251, `<Value>83,5588</Value>`, учитывать `<Nominal>`), запасной — `https://www.cbr-xml-daily.ru/daily_json.js`. Курс обновляется перед каждой синхронизацией цен; если оба недоступны — остаётся последний сохранённый.
- **Таблица `settings`** (ключ → значение) — для того, что клиент меняет из Telegram-панели, а не правкой `.env`: `global_markup_percent`, `rate_premium_percent`, `usd_rub_cbr`, `usd_rub_rate`, `rate_updated_at`, `prices_updated_at`. Пока ключа нет — значение по умолчанию из `.env` (`MARKUP_PERCENT`, `EXCHANGE_RATE_PREMIUM_PERCENT`, запасной `EXCHANGE_RATE_USD_TO_RUB`).
- **Цена лота** = цена FZ × курс × (1 + наценка лота или глобальная) / (1 − fee − payment_fee категории), **вверх до целого рубля**.

### 6.17. Заказы у FZ асинхронные; обработка заказа переделана (1 октября, roadmap 5.2–5.10)

**Из документации FZ** (`reseller.fazercards.com/ru/docs`, `/docs/cookbook`, `/docs/webhooks`; текст есть прямо в HTML страницы):
- Все `POST …/order` отвечают `{"ok": true, "order": {"id": "ord-…", "kind": …, "status": "processing"}}`. Статусы: `processing` → `completed` / `failed` / `refund`. Мгновенные товары — сразу `completed` с кодами в `order.cards`; иначе результат — `GET /orders/{id}` (`order.cards`). Раньше наш код искал `order_id`/`id` на верхнем уровне ответа — номер заказа FZ сохранялся бы пустым.
- Idempotency-Key: тот же ключ → тот же заказ без второго списания; ключи живут 7 дней; тот же ключ для другого типа заказа — 409.
- HTTP: 400 — валидация/бизнес-правило (в т.ч. «Insufficient balance»), 409 — конфликт, 5xx — «осторожные повторы». 429 — с `Retry-After` (клиент уже повторяет сам).
- У FZ есть **исходящие вебхуки** `order.status_changed` (подпись `X-Webhook-Signature: sha256=<HMAC тела>`, повторы через 1/5/30 мин, кодов в теле нет) — настраиваются в кабинете FZ. Пока используем опрос раз в минуту — проще и не требует секрета; вебхук FZ — возможная доработка.
- `POST /topups/validate-id` — проверка ID игрока до заказа (`valid`, `player_name`, иногда `region`) — пригодится для проверки до оплаты (`pre_payment_settings`, «Возможные доработки»).

**Подпись вебхука GGSell:** перебрали 91 тыс. вариантов (перестановки полей id_i/id_d/amount/currency/date/email/ip, разделители, ключи V1/V2 и seller_id в начале/конце, sha256 и HMAC) на реальном вебхуке пилота — совпадений нет. Видимо, отдельный секрет уведомлений. Защита — сверка через `get_order_info`.

**Как теперь устроено** (`app/orders/order_processor.py`, `jobs.py`, `delivery.py`, `app/api/webhooks.py`):
1. Вебхук: проверка `id_i` → 200 сразу → фоновая задача.
2. `register_order`: `get_order_info`, сверка (наш лот, `item_id` = `id_d`, `date_pay`), запись `Order` (оплаченная сумма, выплата продавцу).
3. `claim_order`: атомарно `PENDING → PROCESSING`.
4. Перепроверка цены (отклонение — в заказ), перевод данных покупателя, заказ у FZ (повторы только сеть/5xx/429).
5. `completed` → выдача в чат; `failed`/`refund` → ручной разбор; `processing` → `ORDERED_UPSTREAM`.
6. `scheduler`: `poll_fz_orders` раз в минуту (таймаут 30 мин), `sweep_missed_orders` раз в 5 мин (пропущенные вебхуки и застрявшие заказы).

### 6.18. Синхронизация цен на витрину (1 октября, roadmap 4.1–4.7)

**`list_offers` отдаёт `price` и `currency`** у каждого оффера (вместе со `status`, текстами, `category`) — то есть реальную цену на витрине можно брать оттуда, отдельный запрос на оффер не нужен. `pagination.total_count` на стейдже показывает 999 при трёх офферах — не полагаемся, листаем по `has_next_page`.

**Как устроено** (`app/sync/showcase.py`, вызывается из `refresh_prices_job` после цен FZ):
1. `check_availability` — алерты «пропало / вернулось», «закончилось / снова в наличии» по позициям с лотом, один раз (даты в `Position`). Ошибки FZ 5xx/429 — не «пропало» (`is_gone_error` в `fz_catalog`).
2. `fetch_offers` + `sync_listings` — статус и цена с витрины в `Listing`; нет в выдаче → `archived`.
3. Если `pricer_enabled`: `push_prices` — PATCH `{"price"}` при отклонении ≥ 1% или если текущая цена ниже минимальной маржи (тогда + алерт). 404 → `archived`, 429/5xx → `call_with_retry`.
4. `PRICES_UPDATED_AT` — только после успешной отправки цен.

**Почему цена с витрины, а не из БД:** клиент правит лоты в кабинете сам; на пилоте цена 103310519 стояла 10 ₽ вручную, а в БД — 67 ₽, и прайсер «из БД» считал бы, что всё в порядке. Теперь ручная цена возвращается к расчётной; менять цену отдельного лота — индивидуальной наценкой.

**Проверка на стейдже:** глобальная наценка 15 → 20 → 15%, индивидуальная 30% → снята — витрина каждый раз совпала с расчётом (вверх до рубля, с комиссией категории).

### 6.19. «Деньги зарезервированы… 12 часов» — не проблема (3 октября, roadmap 5.0)

На пилоте у покупателя после оплаты висела плашка «Деньги зарезервированы. Вернём оплату, если продавец не обработает заказ в течение 12 часов», и наше сообщение с товаром её не убрало (`invoice_state` 3, `unique_code_state.date_delivery` null). Боялись, что все заказы через 12 ч вернутся покупателям.

**Проверили:**
- **Естественный эксперимент.** Заказ 53081129 оплачен 01.10 17:47. 03.10 (через 40+ ч) `invoice_state` всё ещё 3, `profit` 9.53, возврата нет. `unique_code_state.state` = 1, даты доставки и подтверждения пустые.
- **Ответ поддержки GGSell (02.10, кратко).** `create-message` только отправляет сообщение и выполненным заказ не отмечает. При `delivery: auto` статус выдачи проставляется автоматически, при `manual` — вручную в кабинете. Отдельного метода API «отметить выполненным» нет. Статус доставки нужен для контроля и напрямую на зачисление средств не влияет.
- **Сентябрьский заказ 51308662.** Продавец тоже только написал в чат. Через ровно 7 суток после оплаты GGSell сам поставил `date_delivery` = `date_confirmed`, `unique_code_state.state` 3, заказ «Завершён», выплата осталась.

**Вывод:** выдача сообщением в чат — достаточная «обработка». Плашка у покупателя висит до подтверждения заказа (покупателем или автоматически через 7 суток), деньги продавцу приходят после подтверждения. Ничего дополнительно (`post_payment_url`, ручная отметка) делать не нужно. Контроль — автоподтверждение 53081129 около 08.10.

Для понимания `unique_code_state.state`: 1 — выдан, но не подтверждён (наш случай); 3 — подтверждён (после 7 суток). Это наблюдение по двум заказам, в документации GGSell не описано.

### 6.20. Telegram-бот администратора и блокировка Telegram в РФ (3 октября, roadmap 6.1–6.8)

**Telegram с российского VPS недоступен.** Стейдж в Москве (AS48282). `api.telegram.org`, `t.me`, `core.telegram.org` не открываются (таймаут), остальной интернет (Google, GGSell) работает. Один из IP Telegram случайно отвечал напрямую, но закреплять его бессмысленно: блокировки меняются. Пользователь во всех проектах использует **прокси только для Telegram**.
- В `.env` — `TELEGRAM_PROXY=http://логин:пароль@хост:порт`. Прокси подключён только у `TelegramClient` (`httpx.Client(proxy=...)`). Системных `HTTP(S)_PROXY` нет: GGSell, FZ и ЦБ ходят напрямую. Проверено: обычный httpx выходит с IP сервера, клиент Telegram — с IP прокси.
- Прокси стейджа: IPv4 shared, Канада, оплачен до 10.10. MTProto-прокси боту не подходят (это протокол приложения Telegram, а не Bot API). Российский выход бесполезен.
- Скорее всего, клиенту на боевом тоже понадобится прокси (2.12).

**Как устроено:**
- `app/clients/telegram.py` — свой минимальный синхронный клиент Bot API на httpx: `sendMessage`, `editMessageText`, `answerCallbackQuery`, `getUpdates`, `setMyCommands`. Асинхронный фреймворк не брали: весь проект синхронный.
- `app/orders/notifications.py::notify_admin` вызывается из того процесса, где возник алерт (app — вебхуки, scheduler — синхронизация и опрос заказов). Пишет в лог и шлёт всем chat_id. Сбой Telegram глотается.
- `app/bot/` — отдельный сервис `bot` (long polling): `views.py` (тексты и клавиатуры, чистые функции от сессии), `handlers.py` (`BotApp`, внешние системы за интерфейсом `Services` — в тестах подделки), `main.py`. Состояние ввода (ждём число, поисковый запрос) хранится в памяти процесса.
- **«Обновить цены сейчас»** бот сам не синхронизирует. Он ставит в настройках `price_sync_requested_at`, а `scheduler` раз в 15 с переносит ближайший запуск джобы `refresh_prices` на «сейчас». Так две синхронизации не идут одновременно (`max_instances=1`). По окончании приходит итог (`price_sync_report_pending`). Смена наценки, надбавки или наценки лота запускает то же самое.
- **Ответ покупателю:** номер заказа берётся из текста сообщения, на которое ответили (`Заказ N`). Отправка — только после кнопки подтверждения: ошибочный reply не уйдёт покупателю.
- Доступ — только chat_id из `ADMIN_TELEGRAM_CHAT_ID` (можно несколько через запятую). Остальные игнорируются.
- `.env` читается при создании контейнера. После правки — `docker compose up -d --force-recreate app scheduler bot`.

**Тесты:** `app/tests/test_bot.py` (26). `app/tests/conftest.py` обнуляет токен в окружении, чтобы тесты не слали сообщения в настоящий Telegram.

**Живая проверка 03.10 и исправления по ней:**
- **Порог 1% и смена наценки.** Синхронизация из бота сначала шла с тем же порогом 1%, что и автоматическая. Наценка 15 → 14% меняет цену меньше чем на 1%, и на витрину ничего не уходило. Теперь при запуске из бота (`price_sync_report_pending` выставлен на старте) `push_prices(threshold_percent=0)`. Порог остался только для автоматической синхронизации раз в 12 ч.
- **Запрос во время идущей синхронизации терялся.** `modify_job(next_run_time=now)` при уже выполняющейся джобе APScheduler пропускает («maximum number of running instances reached … skipped»), а запрос к тому моменту уже был снят. Теперь `refresh_prices_job` выставляет флаг `_running`, и `check_price_sync_request` не забирает запрос, пока синхронизация идёт: он запускается сразу после неё. Проверено вживую: надбавку меняли посреди стартовой синхронизации, и запрос отработал следом.
- **Массовый сбой FZ молчал.** Подписка FZ протухла, 2519/2519 позиций падали с 403, но это было видно только в логе. Теперь `fz_errors_alert` шлёт алерт, если не обновилось ≥ 10% позиций (ошибки «пропало» не считаются), с подсказкой про подписку при 403.
- В итоге синхронизации теперь показывается курс, по которому посчитаны цены (`current_rate` в конце), а не курс на начало.
