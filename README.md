## 📌 О проекте

**FRK GGSell AutoSync** решает задачу продавца цифровых товаров: вручную держать на маркетплейсе тысячи лотов с актуальными ценами и выдавать каждый заказ невозможно. Система делает это сама:

- **Каталог.** Около 2 500 позиций поставщика: пополнения по ID для 40 игр и сервисов, подарочные карты 236 категорий (сервис + регион: Google Play, App Store, Steam, PlayStation, Roblox…), прямое пополнение кошелька Steam в четырёх валютах, Telegram Stars и Telegram Premium.
- **Автозалив.** Для каждой позиции собирается карточка лота по образцу заказчика: русское название, регион, поля для данных покупателя, правила. Затем подбирается листовая категория GGSell, и лот выставляется черновиком.
- **Цены.** Каждые 12 часов система пересчитывает цены по курсу, наценке и комиссии категории и обновляет на витрине только изменившиеся.
- **Заказы.** После оплаты система сверяет заказ, перепроверяет цену у поставщика, покупает товар, дожидается выполнения и отправляет покупателю код или подтверждение пополнения в чат заказа. **Без участия человека, обычно за 2–3 минуты.**
- **Управление.** Через Telegram-бота: алерты, ручной разбор проблемных заказов с ответом покупателю, панель «Авто-прайсер» (глобальная и индивидуальная наценка, надбавка к курсу, выключатель прайсера, обновление цен по кнопке).

Вся цепочка проверена живыми покупками: подарочные карты, пополнение игрового баланса, пополнение Steam, Telegram Stars.

## 🔄 Каталог и синхронизация цен

Каталог поставщика на порядки больше нужного: сотни категорий пополнений, сотни категорий карт и десятки тысяч Steam-игр. Поэтому в `data/` хранятся только категории, утверждённые заказчиком, и импортируются все их номиналы.

**Пакетное обновление.** `refresh_all_positions()` группирует позиции по категории поставщика: один запрос на категорию, а не на позицию. Полный цикл по ~2 500 позициям — около 280 запросов и около 2 минут. Клиент FazerCards соблюдает лимиты API по категориям запросов (каталог, заказы, статусы, аккаунт) скользящим окном и выдерживает `Retry-After` с джиттером на ответе 429.

**Витрина** (`showcase.py`) после обновления цен:

1. **Статус и текущая цена каждого лота** читаются с самого GGSell. Удалённые лоты помечаются архивными, цены по ним больше не отправляются. Цена, изменённая вручную в кабинете, возвращается к расчётной; для отдельного лота цена задаётся индивидуальной наценкой.
2. **Обновляется только поле `price`, и только если расчётная цена отличается больше чем на 1%.** Тысячи лотов не дёргаются из-за копеечных колебаний курса. Исключение — когда текущая цена уже не даёт минимальной маржи: она обновляется сразу, с алертом.
3. **Пропажи у поставщика.** Если позиция пропала у FZ или закончилась (`stock = 0`), приходит алерт, один раз при появлении и один раз при возвращении. Лот не снимается автоматически, решение за администратором.
4. **Отказоустойчивость.** Сбой GGSell не роняет синхронизацию: цены поставщика уже сохранены, следующий запуск дошлёт. Безопасные запросы (чтение, PATCH цены) повторяются при 429, 5xx и тайм-аутах.

Синхронизацию можно запустить и из бота кнопкой «Обновить цены СЕЙЧАС», а также она запускается сама после смены наценки. Бот только ставит запрос в БД, а выполняет его `scheduler` той же джобой. Поэтому две синхронизации никогда не идут одновременно, а запрос, пришедший во время идущей синхронизации, ждёт её окончания.

## 💰 Ценообразование

```
цена лота = цена FZ ($) × курс × (1 + наценка) ÷ (1 − комиссия категории − 2.7% за оплату)
```

- **Курс** = курс ЦБ РФ + надбавка (по умолчанию 5%). Курс ЦБ берётся из XML ЦБ с запасным источником; если оба недоступны, используется последний сохранённый.
- **Комиссия GGSell** у каждой категории своя (от 2% до десятков процентов) и удерживается из цены. Поэтому наценка «чистая»: продавец получает ровно себестоимость × (1 + наценка). Формула подтверждена на реальных продажах: выплата продавцу из API GGSell совпадает с расчётной.
- **Округление вверх до целого рубля** (требование заказчика). У товаров с ценой за единицу (1 ₽ Steam, 1 звезда) — до копейки, иначе 1.33 ₽ превратились бы в 2 ₽.
- **Наценка** — глобальная или индивидуальная для конкретного лота. Обе меняются из Telegram-панели и хранятся в БД, а не в `.env`.
- **Защита от убытка:**
  - перед каждой закупкой цена у поставщика перепроверяется — при росте больше порога заказ уходит на ручной разбор;
  - цена, не дающая минимальной маржи, поднимается немедленно.

## 🏷️ Автозалив лотов

Для каждой позиции `uploader.py` выполняет:

1. **Собирает карточку по образцу заказчика:** «Mobile Legends RU* Алмазы 275 (250+25) | по ID | Автодоставка».
   - Название товара переводится словарём («Diamonds» → «Алмазы»).
   - Регион определяется по названию номинала, затем по конфигурации категории, затем по примечанию поставщика; если нигде не указан — Global.
   - Описание, инструкция и правила — из шаблонов `data/offer_templates.json`, их можно править без кода.
2. **Подбирает листовую категорию GGSell** по правилам: спуск по дереву «игра → регион → номинал» с запасными ветками «Другое количество» / «Другие страны». Из ~2 500 позиций категория подобрана для ~2 250; для остальных на GGSell подходящей ветки нет.
3. **Создаёт оффер черновиком** с заглушкой обложки (обложки и публикацию делает заказчик) и **сразу записывает лот в БД**.
4. **Вешает опции покупателя** по полям, которые требует поставщик: ID игрока, ID сервера, выбор сервера из списка, логин Steam, username Telegram.

**Особенности API GGSell, найденные на практике:**
- **Выбор сервера:** у опции-списка обязателен ровно один вариант по умолчанию. Реальный сервер по умолчанию ставить нельзя, поэтому стоит заглушка «— выберите сервер —», и заказ с ней уходит на ручной разбор.
- **Калькулятор «Заплачу ⇄ Получу»** (пополнение Steam на любую сумму, звёзды поштучно) включается, только если оффер создан сразу в «валютной» категории с диапазоном `min_quantity..max_quantity`. Цена в таком оффере — за единицу, количество приходит в заказе.
- **Требования категорий.** В части категорий оффер публикуется только при наличии обязательной опции покупателя (Telegram Premium) или при минимальной сумме заказа (Telegram Stars — от 150 ₽).

**Повторный запуск безопасен.** Уже созданные лоты не дублируются; если сбой случился между созданием лота и опциями, повторный запуск досоздаёт только опции.

## 📦 Обработка заказов

`order_processor.py` — путь заказа от вебхука до выдачи:

1. **Вебхук.** GGSell сразу получает `200`, обработка идёт в фоне.
2. **Сверка.** Подписи вебхука GGSell не раскрывает, поэтому правдой считается только то, что вернул `get_order_info` по нашему токену: заказ на наш лот, товар совпадает, заказ оплачен. Поддельный вебхук может лишь запустить обработку настоящего оплаченного заказа, а она идемпотентна.
3. **Захват.** Атомарный `UPDATE … WHERE status = 'pending'`: заказ обрабатывает ровно один обработчик, даже если вебхук пришёл дважды или одновременно сработала страховочная джоба.
4. **Подготовка.**
   - Цена перепроверяется у поставщика.
   - Данные покупателя из опций GGSell переводятся в поля поставщика; подпись выбранного сервера сопоставляется с его значением у FZ.
   - Для Steam логин заранее проверяется у поставщика: если его нельзя пополнить, заказ не делается.
   - Для товаров с калькулятором проверяется, что количество в допустимом диапазоне.
5. **Закупка у FazerCards** с `Idempotency-Key` = номер заказа GGSell: повтор вернёт тот же заказ без второго списания.
   - Повторяются только сбои сети, 5xx и исчерпанный лимит 429.
   - Бизнес-отказы («недостаточно средств», неверный ID) сразу уходят на ручной разбор с текстом ответа.
   - Покупки Telegram у поставщика не защищены ключом идемпотентности, поэтому после сбоя связи не повторяются вообще: заказ уходит на ручной разбор с пометкой «мог пройти, проверьте у поставщика».
6. **Ожидание.** Поставщик асинхронный: `created → processing → completed / failed / refund`. Джоба опрашивает его раз в 15 секунд, с тайм-аутом 30 минут.
7. **Выдача.** Сообщение в чат заказа по типу товара: коды подарочной карты, «пополнение выполнено», «баланс Steam пополнен на N RUB», «звёзды отправлены». Если коды не пришли, сырой ответ поставщика покупателю не уходит — заказ идёт на ручной разбор.

**Страховка.** Раз в 5 минут джоба сверяет последние продажи GGSell с базой и обрабатывает те, по которым вебхук не пришёл. Заодно она подбирает заказы, зависшие после перезапуска процесса.

## 🤖 Telegram-бот администратора

Синхронный клиент Bot API на `httpx` (long polling, отдельный сервис) — проект целиком синхронный, асинхронный фреймворк ради бота не нужен.

- **📊 Статус:**
  - курс и наценка;
  - прайсер вкл/выкл, время последнего обновления цен;
  - лоты по статусам, заказы за сутки;
  - баланс поставщика.
- **🤖 Авто-прайсер:**
  - выключатель прайсера;
  - глобальная наценка, надбавка к курсу ЦБ, наценка отдельного лота (поиск по id или названию);
  - «Обновить цены СЕЙЧАС».
- **⚠️ Ручной разбор:**
  - карточка каждого проблемного заказа с данными покупателя и причиной;
  - **ответ (reply) на карточку или алерт уходит покупателю в чат заказа** после подтверждения кнопкой;
  - «Выдан вручную» закрывает заказ.
- **Команды** `/lot`, `/pause`, `/activate`, `/sync`, `/orders`, `/manual`.
- **Доступ** — только chat_id из `.env`, остальные игнорируются.

Алерты отправляются из того процесса, где возникли, с повторами: если Telegram или прокси временно недоступны, алерт не теряется и в любом случае остаётся в логе.

## 🛡️ Эксплуатация

- **Бэкапы.** Сервис `backup` каждую ночь делает `pg_dump` и хранит 7 последних. `ops/restore_check.sh` разворачивает последний дамп во временную базу и сверяет данные с рабочей.
- **Сторож.** Раз в 5 минут проверяет:
  - что `app` отвечает;
  - что бот связывается с Telegram;
  - свежесть синхронизации и бэкапа;
  - место на диске;
  - перезапуски сервисов.

  Алерт приходит один раз при появлении проблемы и один раз при восстановлении.
- **`/health/full`** — для внешнего мониторинга (UptimeRobot): отвечает 503, если БД недоступна или `scheduler` не подаёт признаков жизни. Это закрывает случай, о котором изнутри сообщить некому.
- **Логи** ограничены (10 МБ × 5 на контейнер); токены API в них не попадают.
- **Фаервол:** открыты только 22/80/443. БД слушает только `127.0.0.1`, потому что Docker публикует порты в обход `ufw`.
- **Секреты** — только в `.env`, в репозитории их нет. `scripts/check_env.py` проверяет заполнение и связь со всеми сервисами, не печатая ключи.

## 💡 Ключевые технические решения

**Идемпотентность на каждом шаге заказа.** Деньги покупателя и баланс у поставщика — реальные, поэтому повтор любого шага безопасен:
- запись заказа ловит `IntegrityError` второго вебхука;
- захват — атомарный `UPDATE`;
- закупка — с `Idempotency-Key` = номер заказа (ключи поставщика живут 7 дней);
- там, где поставщик идемпотентность не гарантирует (Telegram), повторов нет совсем.

**Правда — в API, а не во вебхуке.** Формулу подписи вебхука GGSell не публикует. Вместо неё система сверяет каждый заказ через API по собственному токену. Поддельный запрос не может заставить систему купить что-то, за что не заплачено.

**Асинхронный поставщик — отдельный статус и опрос.** Заказ у FazerCards выполняется от секунд до минут. Обработчик не ждёт: заказ переходит в `ORDERED_UPSTREAM`, а результат забирает джоба опроса. Вебхук отвечает мгновенно, а падение процесса посреди ожидания ничего не теряет.

**Минимум запросов к внешним API.**
- Цены поставщика обновляются пакетно, по категориям.
- На витрину уходит только `price` и только при заметном изменении.
- Состояние витрины читается постраничным списком, а не по одному лоту.

**Цена за единицу и калькулятор маркетплейса.** Пополнение Steam на любую сумму и звёзды поштучно не укладываются в модель «один номинал — один лот». Поэтому такие позиции хранят цену одной единицы с точностью 8 знаков (1 ₽ Steam ≈ $0.012), лот создаётся в «валютной» категории с диапазоном количества, а количество приходит в заказе. Остальной конвейер — цены, залив, обработка, выдача — тот же, что у обычных товаров.

**Данные покупателя — через поля поставщика.** Логин Steam и username Telegram описаны как «поля пополнения», как ID игрока. Поэтому создание опций, текст карточки и разбор заказа — общий код для всех типов товаров.

**Настройки, которые меняет заказчик, — в БД, а не в `.env`.** Наценка, надбавка к курсу и выключатель прайсера меняются из Telegram без перезапуска; `.env` задаёт только начальные значения и секреты.

**Одна синхронизация за раз.** Запросы из бота не запускают синхронизацию напрямую, а ставят флаг. Его забирает `scheduler` и переносит запуск той же джобы с `max_instances=1`. Запрос, пришедший во время идущей синхронизации, не теряется, а ждёт её окончания.

**Эмпирическая проверка внешних API.** Документация маркетплейса расходится с реальностью: часть полей нельзя изменить после создания, у пагинации нет `per_page`, у категорий есть неописанные ограничения. Поэтому каждое поведение сначала проверялось на тестовом оффере, а итоговые решения проверены живыми покупками.

## 🧪 Тестирование

268 автотестов (`pytest`, HTTP-API замоканы через `respx` и `unittest.mock`, БД — SQLite в памяти):

- формула цены, комиссии, округление, защита маржи;
- подбор категорий и регионов, сборка карточек, опции и сопоставление данных покупателя;
- синхронизация витрины: порог, ручная цена, архивные лоты, сбои GGSell, повторы;
- обработка заказа: все ветки статусов, повторы и их отсутствие, гонка вебхуков, страховочная джоба, Steam и Telegram;
- Telegram-бот: доступ, панель, ответ покупателю, закрытие заказа;
- сторож, `/health/full`, алерты с повторами.

```bash
python -m pytest
```

## 🚀 Запуск

Установка на сервер, заполнение `.env`, импорт каталога, залив лотов, бэкапы и мониторинг — пошагово в **[INSTRUCTIONS.md](INSTRUCTIONS.md)**.

Коротко (сервер с Docker):

```bash
cp .env.example .env              # заполнить строки «ЗАПОЛНИТЕ»
docker compose build
docker compose up -d db backup
docker compose run --rm app alembic upgrade head
docker compose run --rm app python scripts/check_env.py
docker compose up -d
```
